# Методика сравнительного прогона

Исходные запросы лежат в [benchmark-queries.jsonl](../studies/oss-bsl-corpus-2026-08-10/benchmark-queries.jsonl). Они строятся скриптом из сохранённого корпуса и не размечались человеком.

В набор вошли по 30 проверок трёх типов:

- точное имя процедуры;
- известный статический вызов;
- ссылка на объект метаданных.

Для каждой проверки известен ожидаемый идентификатор chunk. Скрипт считает Recall@1, Recall@5, Recall@10, MRR@10 и nDCG@10. Время запроса измеряется для каждого из 90 запросов через `perf_counter`; p50 и p95 находятся из отсортированного списка задержек. В поле `serialized_index_bytes` записан размер Python-объекта индекса после сериализации pickle, поэтому он нужен для сравнения запусков на том же стеке, а не как размер готового серверного индекса.

| Метод | Что делает | Что показал прогон |
|---|---|---|
| `exact_name` | Ищет процедуру по точному имени | Не работает для запросов на вызовы и метаданные |
| `bm25` | Лексическое ранжирование по BSL-chunk | Лучший Recall@5 и MRR@10 в этом наборе |
| `hash_vector` | Локальное hash-представление без внешней модели | Плохое качество и высокая задержка; это baseline, не семантический поиск |
| `rrf_hybrid` | RRF поверх BM25 и hash-vector | На этом корпусе уступил BM25, потому что слабый vector ranker добавляет шум |
| `graph_context` | Точное сопоставление и ближайшие узлы графа | Высокий Recall@10 на структурных вопросах, но это не полнотекстовый ranker |

Полный результат, окружение, параметры, commit кода, SHA манифестов и все численные поля находятся в [results.json](../studies/oss-bsl-corpus-2026-08-10/results.json). Графики строятся только `scripts/render_charts.py` из этого файла.

В следующем сравнении нужен отдельный набор запросов на естественном языке с полем `review_status`. Пока не будет ручной проверки, такие запросы не должны попадать в публичные итоговые метрики.
